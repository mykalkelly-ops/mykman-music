# MYKMAN Music audit — September 18, 2026

Audited baseline: `8261b72` (Unify comparison queue with Apple Music playlist). Changes were developed in an isolated checkout with synthetic databases. No production database, comparison history, Apple account, or Render deployment was modified during validation.

## Findings fixed

| Area | Bug | Change |
| --- | --- | --- |
| Refill | Queue required both songs to have Apple library IDs. XML-only libraries could never fill it. Rejected candidates triggered hundreds of retries. | Ranking accepts imported songs independently of Apple playlist availability. Batch selection replaces rejection retries. |
| Selection | Exhausted candidate pools silently allowed previously compared pairs. History exclusions stopped at 20,000 comparisons. Overlapping playlists could nominate a song against itself. | Exclude all historical pairs, reject self-pairs, and search beyond exhausted samples before declaring no pair available. |
| Skip | Skip and Tie sent identical payloads; skipping changed ratings and reduced uncertainty. | Skip now advances the queue without adding a comparison or modifying ratings. Tie remains evidence. Historical skip/tie records cannot be separated retrospectively. |
| Vote safety | Double clicks and retries could count twice. The journal fetched the latest global comparison instead of the row just saved. | Frontend request guard, SQLite writer reservation and duplicate-pair validation, journal the actual saved object; complete the queue item in the vote transaction. |
| Placement | Bounds used already-updated opponent ratings; the second song could see the first song's finalized placement rating. | Both bounds use pre-vote opponent ratings. Placement candidates use the closest placed opponent to the midpoint, or highest placed opponent at cold start. |
| Queue UX | Failures could leave no useful feedback; votes reset queue size to four and erased other cards' difficulty/nostalgia choices. | Loading/error status, retry recovery, retained unfinished pairs/preferences, selected visible queue size honored. Stale/deleted/already-compared pairs are removed from active status. |
| Album classification | Any title containing the letters `ep` was classified as an EP, including Reputation. | Require EP as a word or explicit release type. |
| UI | Comparison cards overflowed narrow layouts, lacked keyboard activation, and clicking a nostalgia label could cast a vote. Collaboration names were inserted unescaped. | Wrapping cards, keyboard support, label-click protection, escaped names, live status announcements, nonblocking MusicKit script. |
| Apple playlist | Unsupported DELETE request, incomplete playlist/track pagination, read failures treated as empty playlists, and failed additions sometimes reported success. | Paginate reads, fail closed on read errors, serialize sync attempts, refresh cached developer tokens, use documented append behavior with an honest retained-track message. |
| Logging | Invalid webhook verification tokens were printed verbatim. | Omit submitted token values. |

Refill tops up the persistent queue; it deliberately retains unfinished pairs. Apple playlists now accumulate comparison listening history: older tracks must be removed in Apple Music. Songs without Apple IDs still participate in ranking, but cannot be added to that playlist.

## Efficiency without sacrificing coverage

Measured on the same machine and synthetic 200-song XML-only library, requesting eight pairs:

| Implementation | Pairs returned | SQL statements | Elapsed |
| --- | ---: | ---: | ---: |
| Original | 0 | 2,882 | 0.923 s |
| Fixed | 8 | 15 | 0.052 s |

This fixture demonstrates the broken-path improvement, not a production latency guarantee. Batch selection itself uses three queries irrespective of requested pair count. Queue payloads use one eager-loaded query. Album and artist score calculation now batch-load tracks and songs rather than lazily querying each album's tracklist.

Selection retains uncertainty, rating proximity, low comparison counts, playlist coverage, cross-playlist bridges, play evidence and new-song placement. Play counts guide which questions to ask, not how much a song is liked. Scoring usually considers samples of up to 60 songs. If samples are exhausted, a lazy full search finds an unused pair; history exclusions are never relaxed. That fallback can still be quadratic in a nearly exhausted library. Loading the library and pair history once uses O(songs + comparisons + playlist memberships) memory; very large archives will eventually need indexed candidate queries and incremental history storage.

## Deployment review follow-up

The local deployment review additionally disabled automatic startup metadata repairs
unless `MYKMAN_RUN_STARTUP_REPAIRS=1`: existing alias merges can rewrite comparison
references and delete resulting self-pairs. Normal releases now skip those routines.
Queue refill checks SQLite's actual transaction state so a prior ORM read cannot
bypass the writer reservation. Render configuration includes `/healthz` and explicitly
disables startup repairs. The release remains uncommitted and undeployed.

[`RENDER_DEPLOYMENT.md`](RENDER_DEPLOYMENT.md) contains the full release procedure and
detailed SQL explanation. Its standard-library safety helper opens the source
read-only, creates an online SQLite backup, exports comparisons, and verifies that
every baseline comparison remains unchanged after deployment. This was exercised
only with synthetic databases, including committed WAL data and deliberately changed
rows. No live backup or live comparison-count verification has been performed.

## Remaining risks and prioritized next work

1. **Undo is approximate and can distort ratings.** It resets only two songs, then replays against opponents' current ratings. Store pre-vote rating/RD/volatility/count/placement snapshots for exact future undo. Legacy undo needs a deliberate reconstruction policy; do not silently rerank or delete the existing archive.
2. **Authentication needs hardening before wider exposure.** `auth.py` still falls back to `changeme`; logout clears the browser cookie/cache but leaves the server session row valid; cookies do not set Secure. Require explicit credentials, revoke sessions server-side and add login throttling. Cached tokens also need a multi-worker revocation strategy.
3. **Restore needs maintenance-mode validation.** The guard permits a backup whose comparison count cannot be read, and file replacement is not coordinated with in-flight requests. Validate SQLite integrity/schema/counts, quiesce writers, and restore atomically. No restore was attempted.
4. **Ranking is a heuristic, not a calibrated accuracy percentage.** Single-result Glicko updates, placement overrides and difficulty/nostalgia adjustments differ from a pure rating-period model. Progress thresholds are labor milestones, not statistical confidence. Validate stability with held-out votes and bootstrap rank intervals before tuning weights. Preserve minority tastes and include exploration even for well-played songs.
5. **Metadata can bias aggregate scores.** Unliked tracks are assigned a low anchor, and title-based release/version matching can conflate unknown preference with dislike. Apple artist search selects the first hit. Keep evidence provenance, confidence and manual overrides; review ambiguous artist/version matches before overwriting totals. Song-pool eligibility currently follows the existing all-imported-song behavior and should be made explicit before broad catalog enrichment.
6. **Architecture and operations.** `main.py` remains roughly 4,000 lines; split comparison, import, enrichment, writing and safety services incrementally. Duplicate `/api/artist-search` registrations should be consolidated. Dependencies are unpinned. Add a reproducible dependency lock and CI. Move long enrichment work to a durable job queue with bounded concurrency, timeouts and retry/backoff. Process-local caches/recent-display hints are not shared across workers. The queue remains shared for the single-admin product.
7. **Performance beyond refill.** Large score pages still calculate complete aggregates and render large lists. Add pagination and cache invalidation tied to data revisions. Benchmark real library size and peak memory on Render. The new selection strategy changes scheduling; compare coverage and rank stability over a representative vote replay before further algorithm changes.

## Apple Music API opportunities

Recommended sequence:

1. Map library IDs to catalog IDs, keeping namespaces separate. Batch library-song retrieval supports up to 300 requested IDs. Store storefront, source, fetched time and matching confidence. Preserve XML play/skip counts rather than assuming the web API provides lifetime equivalents. [Apple: multiple library songs](https://developer.apple.com/documentation/applemusicapi/get-multiple-library-songs)
2. Enrich catalog metadata with ISRC, duration, release date, genres, artwork and album relationships. ISRC lookup supports batches up to 25 and can return multiple songs per code: combine recording identity with duration/version checks and retain live/demo distinctions. [Apple: song attributes](https://developer.apple.com/documentation/applemusicapi/songs/attributes-data.dictionary), [ISRC lookup](https://developer.apple.com/documentation/applemusicapi/get-multiple-catalog-songs-by-isrc)
3. Use recently played tracks and heavy rotation as candidate-selection evidence. Recently played tracks requires a music user token and returns paginated results with a maximum page size of 30. These resources are not a complete lifetime listening ledger or a direct preference rating. [Apple: recently played tracks](https://developer.apple.com/documentation/applemusicapi/get-v1-me-recent-played-tracks), [history](https://developer.apple.com/documentation/applemusicapi/history)
4. Cache successful catalog responses by storefront/resource ID; refresh incrementally, follow every `next` page, and retain last-known-good metadata when requests fail. Apply bounded retries to rate limits/transient errors and keep negative matches reviewable. Catalog completeness varies with territory and editions; never equate catalog track count with tracks heard.
5. Keep playlist export optional and honest. The documented endpoint appends tracks; an exact rotating mirror cannot be promised from the currently documented operations reviewed here. [Apple: add tracks](https://developer.apple.com/documentation/applemusicapi/add-tracks-to-a-library-playlist), [API overview](https://developer.apple.com/documentation/applemusicapi/)

These are integration recommendations, not claims that the enrichment pipeline was implemented or tested against an authorized Apple account in this audit.
